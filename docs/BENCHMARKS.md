## Implemented FO-003 foundation

`FixtureWorkspace` discovers the executing test assembly's checkout and creates only a fresh GUID child beneath ignored `artifacts/FO-003-fixtures-20261029/fixtures/`. It accepts no arbitrary target root. After opening the volume root, Windows directory/file operations use single child names relative to retained parent handles with no-reparse semantics. Shared artifact parents use atomic open-or-create; owned run/child directories and files use exclusive creation. Identity/regular-marker checks accompany operations; readback and hashing use retained file handles. Sharing flags alone are not claimed to prevent directory reparse-metadata mutation.

Canonical versioned manifests sort relative names and describe a fixed SHA-256 block recipe, seed, content key, length, expected hash and fixed UTC timestamp. They exclude absolute paths, run IDs and clocks. Expected content hashes are prepared before payload creation; actual hashes are checked through the generated file handle. A separate bounded receipt records run identity, outcome, created/completed counts, actual written bytes, manifest digest and last checkpoint. Cancellation/failure preserves partials; receipt writing remains available after time/cancellation limits when ownership and storage permit. There is no cleanup API or automatic deletion.

Default per-run limits are 64 payload files, 16 directories, 1 MiB per file, 8 MiB total payload, depth 8, 15 seconds and at least 64 MiB free space. Validated hard ceilings are 256 files, 64 directories, 4 MiB per file, 32 MiB total, depth 16 and 60 seconds. Each control file is capped at 1 MiB. Plan admission and chunk writes both enforce resource bounds; a plan rejection creates no payload. Resource limits are safety ceilings, not performance claims.

## Evidence gates

Record each case as Not run, Pass, Fail, Blocked or Not applicable with a concrete reason. Do not substitute a performance number for correctness, a synthetic adapter pass for physical USB acceptance, an integrity check for recoverability, or installer build success for upgrade acceptance. A one-million-row database is not a one-million-file scan result. Initial readiness review needs approved protocols and scoped next tasks; V1 release later needs accepted correctness, performance, security, installation and physical-media results for supported scenarios.

Benchmarks target the mechanisms in [architecture](ARCHITECTURE.md). Baseline/reference limits must be revised through reviewed evidence if hardware or product requirements change, rather than silently weakening a failed test. Record the approved expensive-test time/disk budget before execution and stop on budget breach with partial receipts preserved.
