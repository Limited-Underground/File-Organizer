# Product requirements

Status: proposed acceptance specification for architecture review, 2026-10-28. No application functionality or benchmark result is claimed. File Organizer by Limited Underground is a free installed open-source application for Windows 11, using C#/.NET 10 and SQLite; Linux follows later. Apache 2.0 permits personal and commercial use and community modifications. Core workflows operate without network access.

## V1 acceptance contract

Each requirement must have automated fixture evidence where practical and independent review. Windows/device/installer observations remain separate from host tests. A failed or unsupported capability must be visible; absence of data must never imply success. All scenarios use deliberately generated, disposable fixtures.

| ID | Requirement and measurable acceptance |
|---|---|
| FM-01 | Two independently navigable panes support path entry, parent/back/forward, sorting, selection and keyboard operation. Navigating one pane never changes the other's location or selection. Access-denied and missing paths render recoverable errors. |
| FM-02 | Copy, move, rename and delete produce an explicit operation plan. Copy preserves source bytes; cross-volume move removes source only after destination verification and durable completion. Rename/case-only rename and same-volume moves honor identity checks. Delete defaults to project quarantine; permanent deletion requires a separate explicit confirmation. |
| FM-03 | Queue operations expose queued/running/paused/cancelled/failed/completed states and per-item outcomes. Pause takes effect at a documented chunk boundary; resume validates source and partial destination before continuing. Cancellation leaves source intact and records partial-output disposition. |
| FM-04 | Every target conflict offers skip, rename or replace; no default silent overwrite. A changed destination invalidates an earlier plan. Progress reports verified bytes separately from transferred bytes, throughput over a documented window and ETA only when estimable. |
| FM-05 | File/folder comparison reports additions, removals and differences by relative path and metadata, with an explicit optional content-verification pass. Inaccessible entries and incomplete scans appear as unknown, never equal. |
| IX-01 | Initial scan inventories only selected roots. A completed scan accounts for every enumerated entry as indexed or an explicit error. SQLite state survives restart; cancellation preserves a resumable generation without declaring the scan complete. |
| IX-02 | Incremental detection handles create/change/delete/rename. Watcher overflow, USN discontinuity or unavailable capability marks affected roots stale and schedules reconciliation. Deterministic mutation fixtures converge to a fresh scan's canonical inventory. |
| IX-03 | Search supports name/path, type, size range and modified-time filters with stable pagination. Case behavior follows the volume/directory capability. Search results disclose offline and stale state. Provisional performance targets are in ROADMAP.md; no measured latency is claimed. |
| IX-04 | Volume disconnection retains inventory with last-seen time and offline status. Remount requires validated volume identity; the same drive letter alone cannot reconnect records. Rename tracking uses volume plus native file identity when available and discloses path-only fallback. |
| IX-05 | Snapshots compare complete selected-root generations and report added/removed/renamed/changed/unknown entries. Reconciliation advances its checkpoint atomically only after the corresponding changes are durable. Interrupted generations remain distinguishable from complete snapshots. |
| DU-01 | Duplicate candidates pass size grouping, a documented bounded partial-hash filter and full SHA-256. Partial matches never establish equality. Files changing during reads invalidate cached hashes. Empty files, sparse files and streams receive explicit policy coverage. |
| DU-02 | Same-volume hard links are one physical allocation and never inflate reclaimable bytes. Intentional-backup roots can be marked protected and excluded from destructive suggestions. Duplicate groups show verification time, locations, link count and exclusions. |
| DU-03 | Review creates a dry-run action plan with source identity/version preconditions, bytes reclaimable and recovery path. Applying it revalidates those preconditions; no automatic destructive deduplication or hard-link replacement occurs. |
| ST-01 | Folder totals and largest-file/directory views distinguish logical and allocated size, hard-link counting policy, incomplete access and offline data. Growth comparisons require compatible completed snapshots and expose root/policy changes. |
| ST-02 | Archive organization supports user-selected destinations and reviewable plans using the same transfer engine. Quarantine records original path, identity, action and restoration metadata; it has no automatic expiry or purge. Archive means organizing files in V1; compressed archive authoring is future scope. |
| ST-03 | A backup checkpoint is verified only after all required outputs pass content verification and its manifest is durable. Restore verifies destination conflicts, free space and identity before action, and reports partial failures. Quarantine on the same volume is not a backup; unavailable independent backup destinations block any workflow requiring a backup checkpoint. |
| RS-01 | Durable journal recovery covers process interruption at every transfer state transition. Restart never assumes a side effect did or did not happen from intent alone; recovery inspects identities, partial output and verification records. Completed moves retain sufficient evidence to explain source disposition. |
| RS-02 | Disconnect/reconnect and locked files pause or fail visibly with bounded retry. Reconnected volumes and files are revalidated; wrong-device replacement cannot resume. Permission failures never silently elevate or widen ACLs. |
| RS-03 | Default enumeration does not traverse reparse points/symlinks. Any opted-in traversal detects cycles and root escapes. Before destructive action, reopen and validate identity, parent and link/reparse status to narrow time-of-check/time-of-use risks. Unsupported network/virtual filesystems disclose reduced guarantees. |
| RS-04 | All core workflows pass with network unavailable. Diagnostics omit file contents, redact paths by default and require explicit review before sharing. No telemetry, automatic updates, service installation or elevated background scanning is part of V1's default behavior. |
| RS-05 | Upgrades preserve inventories, operation journals, quarantine metadata and user files. Schema migration has a verified backup and recovery path; incompatible downgrades refuse to open newer schemas. Uninstall defaults to retaining user state with clear instructions for separately authorized removal. |

## Scope and explicit limitations

V1 targets local Windows 11 NTFS and removable filesystems whose capabilities are detected at runtime. Non-NTFS roots use enumeration, notifications where available and periodic reconciliation; they cannot promise USN or stable native identity. Network shares may be browsed only with explicitly documented capability limits and are not part of the initial reliability qualification. V1 does not promise forensic recovery of already deleted files, crash-proof external hardware, filesystem transactions across devices or byte-exact ACL/alternate-stream preservation on incompatible destinations. Transfer plans must disclose supported metadata preservation and any omissions before execution.

Linux packaging/adapters, cloud synchronization, multi-user shared indexing, privileged system-wide scanning, compression formats, automatic destructive cleanup, shell extensions and unattended updates are future enhancements. Future scope does not weaken any V1 requirement above.

## Acceptance ownership

The owner approves architecture, V1 scope and final release acceptance. Maintainers own requirement traceability in the task backlog and link accepted evidence per requirement. Tests establish only their stated environment; simulated disconnects do not establish USB hardware acceptance. Progress is reported as accepted milestone gates and outstanding requirements, without invented completion percentages. Changes to this specification require a recorded reason and owner review when they alter product behavior or safety guarantees.
