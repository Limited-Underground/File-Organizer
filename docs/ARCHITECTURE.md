# Architecture proposal

Status: proposed for owner review, 2026-10-28. No application functionality, database, installer or service exists. This document owns module boundaries, persistence and recovery contracts. [Requirements](REQUIREMENTS.md) owns behavior; [benchmarks](BENCHMARKS.md) owns feasibility evidence.

## Deployment and ownership

Use one modular desktop product, one per-user worker and one local SQLite database. Prefer Avalonia MVVM on .NET 10/C# for the Windows 11 desktop; keep platform calls outside view models and domain policies. A later Linux adapter reuses policy and engines, not Windows assumptions. Do not create network services, a second inventory database or separate duplicate/transfer implementations.

Planned source directories are boundaries, not a request to create placeholder projects:

| Module / planned location | Owns | Interface contracts and permitted dependencies |
|---|---|---|
| Desktop / `src/FileOrganizer.Desktop` | Dual panes, queue, comparisons, duplicate review, storage views, settings, accessibility | MVVM; calls application commands and paginated queries only. Never performs file mutations or SQL directly. |
| Core / `src/FileOrganizer.Core` | Identities, operation states, conflict policy, verification rules | Pure C# records/policies. No UI, SQL, native calls or service lifecycle. |
| Application / `src/FileOrganizer.Application` | Use cases, task coordination, authorization and cancellation | `PlanOperation`, `SubmitPlan`, `Pause`, `Resume`, `Cancel`, `GetOperation`, `QueryInventory`; depends on Core and ports. DI composition lives in host. |
| Filesystem Windows / `src/adapters/FileOrganizer.Windows` | Handle identity, metadata, enumeration, native change feed, safe file I/O | Implements `IFileSystem`, `IVolumeCatalog`, `IChangeFeed`. Capability results distinguish supported, unavailable, denied and transient failure. |
| Persistence / `src/FileOrganizer.Persistence` | SQLite queries, bounded transactions, migrations, durable state and backup | Implements `IInventoryStore`, `IOperationJournal`, `ISnapshotStore`. Single write coordinator. |
| Engines / `src/FileOrganizer.Engines` | Scan/reconcile, transfer, duplicate analysis, search aggregates, archive/quarantine | Application invokes engines; engines consume ports. Archive and quarantine use the same transfer engine. |
| Worker / `src/FileOrganizer.Worker` | Engine lifetime, scheduling, database writer and IPC endpoint | Per-user .NET Generic Host; exclusive profile lock prevents two writers/engines. |
| Future Linux adapter | Linux identity, enumeration and change notifications | Implements existing capabilities; inode/device identity and case semantics are platform-specific. No empty adapter is required now. |

`IFileSystem` returns async bounded enumeration, open handles, identity/metadata probes, exclusive temporary creation, stream I/O, flush, rename, delete and link metadata. Operations return typed outcomes including access denied, unavailable volume, sharing violation, unsupported metadata and stale identity. Native handle lifetimes remain with the adapter; cancellation disposes them. An enumeration error is a recorded coverage gap, never an empty directory. UTC timestamps are observations, not identity or proof of unchanged bytes.

Unit tests target policies, integration tests use disposable filesystems/databases, and installation/device scenarios run separately. Pin actual package versions and validate licenses when dependencies are introduced; a recommendation is not a dependency lock.

## Process and IPC contract

Recommend a normal unelevated per-user worker executable, started by the desktop. It may finish explicitly submitted work after the UI closes only after clear user choice. Login auto-start is opt-in. No Windows Service or automatic elevation in V1. A service would broaden privileges, user-session coordination and attack surface without a demonstrated requirement. Background jobs use the same application services whether hosted together in early tests or in the worker.

Use local Windows named pipes with current-user access control, peer identity checks, local-only endpoint policy and bounded message sizes. The worker does not impersonate clients or accept arbitrary executable commands. Use a versioned envelope: protocol version, request ID, command, payload and response/error. `SubmitPlan` carries a durable idempotency key; retry returns the existing operation. Events have sequence numbers; reconnect queries a snapshot then resumes events from a cursor, or resynchronizes after retention expiry. Cancellation acknowledgment means accepted request; only terminal journal state means cancellation finished. Negotiate incompatible versions before any mutation. Linux can substitute a user-permission Unix domain socket.

Only the worker opens the database for writing; desktop reads through IPC, preventing stale database access during migrations. The worker validates plan paths, volume identities and destructive preconditions immediately before I/O. Same-user IPC isolation does not protect against malware already executing as that user. See [.NET named pipes](https://learn.microsoft.com/en-us/dotnet/api/system.io.pipes.namedpipeserverstream).

## Inventory, identity and change detection

Persist file objects separately from directory entries: multiple names may point to one object. On supported Windows volumes use handle-derived volume serial plus 128-bit file ID, supplemented by volume GUID and a local inventory volume-generation identifier. Drive letters and labels are mount observations. IDs can be reused after deletion; cloned/reformatted volumes may collide. Reconnect compares identity, filesystem and observations; ambiguous clones require user selection/new inventory generation. Never merge identities solely by drive letter. Unsupported IDs use a clearly marked path-based fallback, with weaker rename detection. [FILE_ID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info) defines the native identity pair.

Preserve original path spelling and per-directory case-sensitivity; do not globally lowercase paths or use SQLite NOCASE as Windows path identity. Resolve paths from parent/name entries and bounded ancestry with cycle protection. A hard link is another entry for the same object, not an additional reclaimable content copy. Directory logical size and distinct-object bytes are separate metrics; allocated bytes may remain unknown on unsupported filesystems.

Initial scan records a generation and coverage per root. Capture change-feed position before enumeration where possible; enumerate without following reparse points by default; replay changes after enumeration, then reconcile changed subtrees. Commit entry observations and feed checkpoint together. Missing entries become deleted only after their parent/root was successfully enumerated in that generation. Offline, denied, cancelled or interrupted roots remain incomplete. Never infer deletion from offline media.

USN is an optimization on supported NTFS volumes, not the authority for current file state. Store journal ID, next USN and volume generation. On restart query journal boundaries including FirstUsn, LowestValidUsn and NextUsn: absent/recreated journal, cursor below a valid boundary, parse error or identity mismatch marks affected coverage stale and schedules full reconciliation. Do not create/resize a system journal to make the application work. Access denied falls back to FileSystemWatcher plus periodic reconciliation without elevation. Journal rename fragments and duplicate notifications trigger identity probes, rather than blindly applying path edits. Capability-specific privilege and record-version support needs a disposable prototype. [Windows change journals](https://learn.microsoft.com/en-us/windows/win32/fileio/change-journals).

FileSystemWatcher is a low-latency hint stream. Coalesce bursts and rescan affected directories; overflow/error marks coverage uncertain and schedules reconciliation. Disconnected roots retain their last-known inventory with observation time and Offline status. At startup reconcile roots changed while the worker was absent. Proposed defaults: reconcile active roots every 24 hours plus startup/overflow/gap triggers, configurable with I/O budgets; user can request reconciliation sooner. An active scan exposes incomplete coverage until complete. Watchers do not guarantee every event. [FileSystemWatcher](https://learn.microsoft.com/en-us/dotnet/api/system.io.filesystemwatcher).

## SQLite proposal

One `inventory.db` per user profile on a local fixed disk. Microsoft.Data.Sqlite with explicit parameterized SQL and versioned migrations is recommended over an ORM initially; the schema needs bulk writes, stable paging and clear journal ordering. Its async ADO.NET methods execute synchronously, so isolate database work on the bounded worker scheduler rather than the UI thread. See [Microsoft.Data.Sqlite async limitations](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/async). Below is a logical schema proposal, not executable SQL:

| Table | Keys and important columns |
|---|---|
| `SchemaMigration` | version PK, checksum, applied UTC; application compatibility metadata |
| `Volume` | local volume ID PK, generation, GUID/serial/filesystem, capabilities, state, last seen; mount observations separate |
| `Root` | root ID PK, volume FK, native identity/path, enabled, coverage status, last complete generation |
| `FileObject` | object ID PK, volume FK, native ID BLOB, identity generation, kind, size, allocated bytes nullable, mtime, attributes, observed token |
| `DirectoryEntry` | entry ID PK, parent object FK, object FK, original name, comparison key/case mode, scan generation, tombstone |
| `ScanRun` / `ChangeCheckpoint` | root/run status and coverage/errors; volume journal ID, next USN, last successful reconcile |
| `ContentHash` | object FK, observed token, algorithm/version, stage, range description, digest, verified UTC; composite uniqueness |
| `Snapshot` / `SnapshotEntry` | snapshot ID and coverage; immutable selected metadata projection with entry/object references and captured values |
| `Operation` / `OperationItem` | operation ID, idempotency key, plan, state, source/destination identities, policy, expected sizes, partial path, durable offset, verification and failure |
| `OperationEvent` | operation FK, sequence PK within operation, state transition, reason and UTC |
| `QuarantineEntry` / `BackupCheckpoint` | original identity/path, retained location, operation FK, verified digest, retention intent, restore status |
| `UserPolicy` | explicit archive/backup exclusions, conflict preferences and configuration version |

Required indexes: live children `(parent_object_id, comparison_key, entry_id)`, native identity `(volume_id, native_id, identity_generation)`, size candidates `(kind, size, object_id)`, changed objects `(volume_id, observed_token)`, hash candidate `(algorithm, stage, digest, object_id)`, operation recovery `(state, operation_id)` and event paging `(operation_id, sequence)`. Name queries use indexed prefix search with explicit case semantics; arbitrary substring search may need FTS5/tokenization after measured evaluation. Sorts always include a stable ID tie-breaker. Keyset paging avoids large OFFSET walks. Bound query count, page size and snapshot retention; benchmark before adding indexes/closure tables.

Enable foreign keys on every connection, WAL for local concurrency, busy timeout, bounded batched writes and `synchronous=FULL` for durability-sensitive transactions. Persist operation state in the same database as inventory, but inventory updates may lag actual I/O and never establish transfer success. Writes go through one coordinator; run file I/O outside SQL transactions. SQLite commit cannot atomically include filesystem operations. Checkpoint WAL during idle windows; monitor its size and close long read transactions. Network-hosted databases are unsupported. [SQLite WAL](https://www.sqlite.org/wal.html) describes concurrency and local-host constraints; choose a patched bundled SQLite version at implementation.

Migration: acquire exclusive profile lock, stop new jobs, settle/checkpoint active work, use SQLite online backup to a dated local recovery copy, verify the copy, then run a transactional forward migration with schema checksum. Test restoration before release. Disk-space shortage aborts before mutation. Older binaries refuse newer schemas. Binary installer rollback does not authorize schema downgrade: restore the matching backup only through explicit recovery when no later journal work would be lost. Never copy only the main database file while WAL is active. Startup integrity failures preserve the damaged set and backups; offer recovery rather than silently replace durable journals. Inventories are rebuildable; operation/quarantine records are not disposable.

## Transfer and recovery contract

State machine: `Planned -> Queued -> Running -> Verifying -> CommitPending -> Completed`; explicit branches to `PauseRequested -> Paused`, `CancelRequested -> Cancelled`, `WaitingForVolume`, `Conflict`, `Failed` and `RecoveryRequired`. Each item tracks its own phase; a queue completion aggregates terminal item outcomes rather than hiding failures. Pause/cancel are cooperative safe-point requests, never claims that a partially executing OS call was rolled back.

1. Plan: enumerate source entries without traversing reparse points, capture handle identity and metadata, destination capabilities, required space and explicit conflict choices. A plan is previewable and expires if preconditions change. Never overwrite an unexamined destination. Unsupported streams/ACLs/sparse/compression/encryption metadata must be disclosed; V1 cannot claim a verified full-fidelity copy when only primary content is preserved.
2. Before writing: revalidate source and destination, journal intent durably, then create a unique exclusive sibling partial on the destination volume. Track its handle identity. Existing destination is retained until approved replacement commits. Bound memory and queued I/O; default one transfer stream per destination device, tuned only with evidence.
3. Copy: advance a durable checkpoint only after bytes are flushed and the checkpoint transaction commits. A checkpoint stores source identity/size/change observation, partial identity, verified range information and offset. Progress shows written versus durably checkpointed bytes separately. Proposed chunk/checkpoint sizes are benchmark parameters, not guarantees.
4. Resume: require the same source observation and partial identity, verify the saved prefix/ranges and partial length, truncate uncommitted trailing bytes when safe, then continue. If identity, size or content preconditions disagree, preserve evidence and offer restart as a new attempt. Timestamps alone do not prove unchanged source. Detect mutation during copying/hashing; use restrictive sharing where possible and fail/retry if a consistent read cannot be established. No V1 VSS promise.
5. Verify: compare complete source and destination SHA-256 from stable handles; verify source is still the approved object and content observation. A successful streaming hash alone is insufficient when resume or concurrent changes could hide corruption. Verification mismatch blocks promotion and source deletion. Files opened concurrently without stable content guarantees cannot be labeled verified.
6. Commit: persist `CommitPending` and verified identities; close/flush handles as required; promote the partial using a same-volume filesystem operation with checked conflict preconditions. SQLite and filesystem are reconciled after a crash by inspecting both candidate identities/hashes. Replacement retains a recoverable prior destination according to the selected policy; never delete it first to create room. Document unsupported atomicity/durability limitations per filesystem.
7. Move: same-volume rename uses checked identities and a durable intent; cross-volume move is verified copy followed by separately journaled source deletion. Reopen/revalidate the exact source immediately before deletion; a changed source is retained. Crash after promotion but before deletion yields a recoverable extra copy, never assumed permission to remove an unknown file. Mark completed only after probing intended final state and recording it durably.

On restart, reconcile every nonterminal item before executing more work: partial absent, destination promoted, backup retained and source removed are distinct observations. Idempotency keys prevent duplicate submissions; observed identities prevent a stale pathname deleting a replacement. Never blindly replay destructive actions. Missing volumes wait for matching identity, with no destructive timeout. Locked/denied items receive bounded retry and actionable status without privilege escalation. Cancellation stops future work and preserves existing source/destination plus partials until the user chooses cleanup; it does not undo completed transfers.

Default reparse/symlink policy is no traversal and no transformation into ordinary file content. Explicit link-copy support requires target-preserving semantics and tests before acceptance. Validate parent directory identity through commit to mitigate path substitution; reject unsafe reparse traversal and self-copy/ancestor destination loops. Adapter design must demonstrate handle-based or equivalently race-resistant mutations before destructive V1 acceptance. Never erase ACLs or take ownership automatically.

## Duplicate, search, archive and quarantine

Group distinct physical objects by size, then deterministic sampled ranges, then full SHA-256. Sampling only filters; neither matching names nor samples establish duplicates. Hash cache is invalidated on uncertain change coverage, source change or identity reuse. Before executing a duplicate action, hash/identity-check the selected objects again. Hard links are displayed as aliases with no false reclaimable-byte claim. User-declared backup/archive roots are marked intentional and excluded from default cleanup suggestions. No automatic deletion or hard-link conversion.

Search is a paged inventory query with observed freshness and coverage. Folder-size aggregates separate logical bytes, distinct-object bytes and unknown/inaccessible portions. Snapshot comparison reports added, removed, renamed, changed and unresolved entries against captured coverage. Rename classification requires stable identity; path-only or ambiguous matches remain uncertain rather than claiming a proven rename. Historical entries cannot authorize filesystem mutations.

Archive V1 means a user-selected folder organization plan using the transfer engine, not a new compression engine. Quarantine is a user-approved move to a selected protected location with a durable original-path/identity manifest and verified content. Same-volume quarantine is preferred; cross-volume quarantine uses verified copy before removal. A backup checkpoint references verified retained content and a restorable manifest; it is not merely an inventory snapshot. Preview restore conflicts and use the same transfer verification contract. No automatic expiry purge; no promise that application data uninstall removes or retains arbitrary user-selected quarantine without explicit policy.

## Installed storage, upgrades and diagnostics

| Location | Decision and rationale |
|---|---|
| `%ProgramFiles%\File Organizer` | Recommend signed machine-wide installed binaries, read-only to ordinary users; installer elevation only. No live database, mutable config or logs here. Actual path follows OS environment rather than hard-coded drive. |
| `%ProgramData%\Limited Underground\File Organizer` | Reserve for installer-owned machine policy only when needed; no shared per-user inventory or unrestricted writable executable content. Not required for ordinary V1 data. |
| `%LOCALAPPDATA%\Limited Underground\File Organizer` | Per-user `data/inventory.db`, schema backups, logs, cache and settings; inherited user ACLs verified. Background process runs as that user. No sensitive database in cloud-synced/network directories. |
| User-selected volumes | Actual file content, verified backups and quarantine; capacity/identity checked and manifests retained. Not a hidden cache under application binaries. |

Recommend MSI with WiX subject to current tooling license/fee review and owner approval; compare MSIX in the technology evaluation. Install scope remains an owner decision. Upgrades request worker quiescence, block new submissions, preserve all data and resumable operations, migrate through application startup, and refuse incompatible worker/desktop combinations. A failed upgrade preserves the previous usable binary/data pair where feasible; database migration recovery is independent of MSI transaction rollback. Signing and update delivery require a later release decision. No silent updater in foundation work.

Uninstall removes binaries and registration, retains inventories, settings, journal and quarantine manifests by default, and clearly reports their location. Any optional removal requires a separate explicit choice and never deletes user file trees or unresolved operation evidence. User data can be exported/backed up before removal. Reinstall recognizes supported retained schemas and offers safe migration.

Proposed limits for acceptance: rotate logs at 10 MiB with five files; cache ceiling 512 MiB with LRU removal of reproducible cache only; retain at least the last two verified schema backups and never prune a backup required by an unresolved migration. Show retention and size in settings. Active database, journals, partial transfers, quarantine and verified checkpoints are excluded from cache eviction. Monitor free space before writes and backups; out-of-space leaves source untouched and a recoverable state.

Use structured events with operation IDs, durations and typed error codes; default logs redact filenames, paths and content. Detailed path diagnostics are opt-in and local; exporting diagnostics previews/redacts fields. No telemetry or network dependency for core operation. Configuration is versioned, validated and atomically replaced; corrupt settings recover from last known valid copy with notice. Query cancellation, bounded queues and rate-limited progress keep the UI responsive. Never log credentials, file contents or IPC secrets.

## Review gates

Owner review must accept the per-user unelevated worker, install scope/tooling and proposed retention defaults. Technical gates are disposable proof of stable identity and safe mutation, USN capability/fallback, durable transfer crash recovery and database migration restoration. These gates permit small explicitly authorized implementation tasks later, not a claim that V1 reliability is already demonstrated. Linux implementation, VSS, cloud/network synchronization, compression, automatic deduplication and machine-wide service operation remain future enhancements.
